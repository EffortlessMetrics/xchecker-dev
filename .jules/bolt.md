## 2024-05-23 - RegexSet Pre-filtering for Secret Detection
**Learning:** Iterating through 40+ complex regex patterns for secret detection on every file is a significant CPU bottleneck. The `regex::RegexSet` type allows compiling multiple patterns into a single automaton that can check for *any* match in a single pass (roughly equivalent to `pattern1|pattern2|...`).
**Action:** When performing multi-pattern matching where the negative case (no match) is common, always use `RegexSet` to pre-filter content before running individual regexes for extraction/replacement. This reduced redaction overhead significantly.

## 2024-06-25 - Redaction Performance & String Replacements
**Learning:** The previous implementation of `redact_content` used `replace_range` inside a loop while iterating over matching lines with computed global byte offsets (using `.lines().take(...).map(|l| l.len() + 1).sum()`). This `O(M * N)` approach caused massive memory shifts and catastrophic slowdowns on files with many secrets. Additionally, assuming `l.len() + 1` for newline lengths broke byte offset calculations on CRLF files, and multiple matches on the same line overwrote each other due to repeated string rebuilds without state tracking.
**Action:** Always prefer `O(N)` single-pass string reconstruction over repeated in-place `replace_range` calls when applying multiple string replacements. In `redact_content`, grouping matches by line number and rebuilding the file line-by-line using a `HashMap` lookup transforms the complexity, fixes CRLF offset issues inherently, and cleanly handles multiple matches on the same line.
